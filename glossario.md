# Termômetro Financeiro — Glossário de conceitos técnicos

Explica, em português simples, os termos técnicos que aparecem espalhados no [CLAUDE.md](CLAUDE.md), no [melhorias.md](melhorias.md) e no [supabase-admin.md](supabase-admin.md) — pra não precisar parar e pesquisar cada um. Cada entrada tem uma analogia e, quando existe, o ponto exato do projeto onde o conceito aparece.

Organizado por área. Use Ctrl+F pelo termo.

## Autenticação e segurança

- **Auth (autenticação)** — a parte do sistema que confirma "você é quem diz ser" (login/senha). No projeto, isso é 100% terceirizado pro Supabase Auth — não escrevemos nenhum código de verificação de senha, criptografia de sessão, etc. Ver `doLogin`/`logout` no `.html`.
- **RLS (Row Level Security, "segurança em nível de linha")** — uma regra que o próprio banco de dados aplica, dizendo "esse usuário só pode ver/editar *estas* linhas da tabela, nunca as de outro usuário". É a única camada de proteção dos dados no projeto hoje (ver [supabase-admin.md](supabase-admin.md)) — não existe um "servidor" separado verificando isso, é o Postgres mesmo que recusa a operação. Analogia: um arquivo de gavetas onde cada gaveta só abre com a chave de um funcionário específico, mesmo que todos estejam na mesma sala.
- **JWT (JSON Web Token)** — um "crachá" digital que o Supabase Auth entrega depois do login, provando quem é o usuário nas próximas requisições, sem precisar mandar a senha de novo a cada clique. É o que carrega o `auth.uid()` que a RLS usa pra decidir "essa linha é sua ou não".
- **anon key vs. service_role key** — duas chaves diferentes de acesso ao Supabase. A `anon` (a que está no `.html`, pública) só abre o que a RLS permite — é segura de expor, mesmo estando no código-fonte que qualquer um pode ver no navegador. A `service_role` ignora a RLS completamente (acesso total de administrador) e **nunca** pode aparecer em código que roda no navegador do usuário — só em algo que roda no servidor (ver "Edge Function" abaixo). Detalhe em [supabase-admin.md](supabase-admin.md).
- **Edge Function** — um pedacinho de código que roda nos servidores do Supabase, não no navegador do usuário. Usado quando uma operação precisa da `service_role` key (ex: apagar a conta de login de verdade, hoje no backlog) — o navegador nunca vê essa chave, só pede pra Edge Function fazer a operação por ele.
- **PBKDF2 e AES-GCM** — dois algoritmos de criptografia usados na *versão anterior* do login (antes do Supabase), quando os dados ficavam só no navegador. PBKDF2 transforma a senha digitada numa chave de criptografia (de propósito: é lento, pra dificultar tentativa de adivinhar a senha por força bruta). AES-GCM é o algoritmo que de fato embaralha/desembaralha os dados usando essa chave. Ficaram obsoletos quando o app passou a usar Supabase Auth, mas o termo "zero-knowledge" (abaixo) vem dessa época.
- **Zero-knowledge** — um modelo onde nem o próprio app/serviço consegue ler os dados do usuário, só quem tem a senha certa. Era o caso da versão local com PBKDF2+AES-GCM. Deixou de ser verdade quando migramos pro Supabase: hoje os dados ficam em texto no banco, protegidos por RLS + TLS + criptografia em repouso do provedor — mais prático (multi-dispositivo, recuperação de senha), mas com uma garantia mais fraca (quem administra o Supabase, hoje só você, consegue ler os dados de qualquer usuário via Table Editor).
- **XSS (Cross-Site Scripting)** — uma falha onde texto digitado por um usuário (ex: nome de um ativo de investimento) acaba sendo interpretado como código e executado na tela de outra pessoa. Mitigado sanitizando entradas na origem (ex: ticker de ativo só aceita `[A-Z0-9]`, ver `addNewAsset`) e escapando `<` em campos exibidos (ex: e-mail no menu de perfil).
- **SRI (Subresource Integrity)** — um "hash" (impressão digital) colado junto da tag `<script>` que carrega a biblioteca `supabase-js` via CDN. Garante que, se o arquivo servido por aquele CDN for adulterado, o navegador *recusa* executá-lo (o hash não bate mais) em vez de rodar código malicioso silenciosamente.

## Banco de dados

- **Postgres** — o banco de dados relacional que o Supabase usa por baixo dos panos. Quando os docs falam em "SQL Editor" ou "schema", é sobre esse banco.
- **jsonb** — um tipo de coluna do Postgres que guarda um documento JSON inteiro (parecido com um objeto do JavaScript) numa única célula da tabela, em vez de espalhar cada campo numa coluna própria. O projeto usa isso pra guardar `months_data`/`investments_data` — é literalmente a mesma estrutura que antes ficava no `localStorage`, só que agora numa coluna do banco. Trade-off: rápido de implementar (não precisou redesenhar a estrutura de dados), mas dificulta consultas tipo "some todos os aportes de todos os usuários no mês X" (exigiria "abrir" o JSON no SQL). Ver decisão registrada em [decisoes.md](decisoes.md).
- **Normalização relacional** — o "jeito tradicional" de modelar um banco: uma tabela por tipo de coisa (ex: `transactions`), com relações entre elas por ID (`user_id`), em vez de um blob de JSON. Desde 01/09/2026, os itens de gasto categorizados (Saída/Diário) já usam esse modelo (tabela `transactions`) — `months_data`/`investments_data` continuam em `jsonb`. Ver [decisoes.md](decisoes.md) pra quando compensa um e quando compensa o outro.
- **Trigger** — uma regra que o banco executa automaticamente quando algo acontece. O projeto tem uma: toda vez que alguém termina o cadastro (`auth.users` ganha uma linha nova), o banco cria automaticamente a linha correspondente vazia em `user_data`.
- **on delete cascade** — uma regra de "efeito dominó": se a linha de um usuário em `auth.users` for apagada, o Postgres apaga automaticamente a linha correspondente em `user_data` (e, do mesmo jeito, todos os itens dele em `transactions`), sem precisar de um segundo passo manual.
- **PostgREST** — o serviço que transforma o Postgres numa API que o navegador pode chamar diretamente (é o que faz `supabase.from('user_data').select(...)` funcionar sem escrevermos nenhuma rota de servidor). É o motivo de não existir "API própria" no projeto — o PostgREST + RLS já cumprem esse papel.
- **Índice (index)** — uma estrutura que o banco mantém "por baixo dos panos" pra achar linhas rápido sem precisar varrer a tabela inteira, parecido com o índice remissivo de um livro. `transactions` tem um índice em `(user_id, date)`, porque toda consulta relevante do app (carregar os gastos de um usuário) já filtra por esses dois campos.

## Frontend / JavaScript

- **IIFE (Immediately Invoked Function Expression)** — um jeito de escrever "todo o código do app dentro de uma função que já roda sozinha", pra manter variáveis internas privadas (não "vazam" pra fora e não colidem com nada). É por isso que o `<script>` inteiro do `.html` é um bloco só, sem várias declarações soltas no nível global.
- **Debounce** — uma técnica de "espera um pouquinho antes de agir, e se acontecer de novo antes desse tempo passar, reinicia a espera". Usado em `saveData`/`saveInvestments` (600ms): se você digita rápido em várias células, o app não manda uma requisição de rede por tecla — só manda depois que você parou de digitar por 600ms. Evita sobrecarregar o backend e reduz risco de uma resposta de rede "atrasada" sobrescrever um dado mais novo.
- **CDN (Content Delivery Network)** — servidores externos usados só pra baixar coisas que o projeto não hospeda ele mesmo: a fonte Inter (Google Fonts) e a biblioteca `supabase-js`. É a única razão de o app "de arquivo único" ainda depender de internet pra carregar certos recursos.
- **Diffing (e a ausência dele aqui)** — em frameworks como React, "diffing" é a técnica de comparar a tela antiga com a nova e mudar só o que precisa. Este projeto **não faz isso**: cada `render*()` reescreve o HTML inteiro da tela (`innerHTML`) e reconecta todos os listeners do zero a cada mudança de estado. Mais simples de entender e debugar num projeto sem build/framework, mas menos eficiente — irrelevante na prática pro tamanho de dados deste app.

## Termos de produto/negócio (contexto rápido — detalhado em [logica-financeira.md](logica-financeira.md))

- **Saldo de abertura** — quanto dinheiro "já estava lá" no primeiro dia de um mês, calculado automaticamente a partir de como o mês anterior terminou (nunca digitado à mão, exceto no primeiro mês do histórico).
- **Preço médio (PM)** — o preço médio pago por uma unidade de um ativo de investimento, recalculado automaticamente a cada compra/venda a partir do zero — nunca fica "desatualizado" porque não é armazenado como valor fixo, é sempre recomputado do histórico.
- **Rentabilidade ponderada** — o retorno percentual da carteira inteira (não de um ativo isolado), calculado como `(valor atual − valor investido) ÷ valor investido`.
